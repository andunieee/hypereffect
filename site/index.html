hypereffect

A simple protocol for describing server-guided, reactive interfaces that can be rendered anywhere.

  1. A client, the renderer, starts the session by sending hello. It knows nothing about the application yet.

    renderer → server 
    hello {}

  2. The server answers with the state, as signals, and a few elements. The renderer draws them with its own native widgets, in its own style.

    There is a fixed set of eighteen components, and they carry semantic variants, not styles: h2 or primary, never a colour or a margin.

    server → renderer 
    signal {"count":0,"_help":false}
element {"id":"main","type":"column"}
element {"id":"label","type":"text","parent":"main","variant":"h2","text":{"cel":"'Count: ' + string(s.count)"}}
element {"id":"inc","type":"button","parent":"main","variant":"primary","label":"Add one","onPress":{"action":"increment"}}

  3. Elements declare up front the few interactions they support. When the user acts, a handler can do only two things:

    • change the state locally, and every attribute that depends on it is recomputed: pressing Help sets _help, and the hint appears;
    • fire an action, like increment above.
    server → renderer 
    element {"id":"help","type":"button","parent":"main","variant":"plain","label":"Help","onPress":{"patch":{"_help":true}}}
element {"id":"hint","type":"text","parent":"main","variant":"caption","text":"Press Add one to count.","visible":{"cel":"s._help"}}

  4. Actions are sent to the server, with the current signals. Local signals, whose names start with _, stay on the client.

    renderer → server 
    action {"name":"increment","signals":{"count":0}}

  5. The server decides what happens next. It can send new elements, replace or remove existing ones, or send signal updates that are merged into the client's state, which may change the interface again.

    Here the label now reads Count: 1 without being re-sent: its text is an expression.

    server → renderer 
    signal {"count":1}
element {"id":"inc","type":"button","parent":"main","variant":"primary","label":"Add another","onPress":{"action":"increment"}}
remove {"id":"help"}

Why

Every program still builds its own interface

For decades, each new kind of computer came with an operating system written just for it, and the same work was repeated until a shared one took over. Phones went through it only recently, until Android.

Interfaces are still at that stage. Useful software that needs to take input from people and show them results invents its own interface, often from raw bytes on a screen or a serial line. Even with a cross-platform toolkit or a whole web browser underneath, the interface is still built from zero, once per program.

hypereffect is the shared layer. It provides the bare minimum needed for most of what software asks of people, in a form that is safe and simple: a renderer is written once per platform and works with any number of servers.

Use cases

Interfaces that are mostly text, inputs, buttons and lists, with the logic on a server or in another process.

Sandboxed modules

A WebAssembly module can render structured information and get input from a user without having to paint each pixel.

Control panels for hardware

A device serves its own control panel over a socket or serial line, the controller gets a clear and native UI.

Alternative browser ecosystem for simple services

A service speaks hypereffect at a URL and looks native in a generic hypereffect browser.

Interfaces generated by agents

An LLM agent builds forms and choices on the fly, as plain JSON with no code to run.

Non-use cases

Places where an application is better served by an interface built for it.

Visual, highly interactive interfaces

Data visualization, editing photos, audio or video, action games, navigating a map: anything drawn or manipulated directly rather than described as text, inputs and buttons.

Tools people live in

Software used all day, where comfort, visual polish and shortcuts that build into muscle memory matter more than anything, even when the content is plain text.

Dense, busy screens

Applications that show a lot at once with many potential actions always within reach of the user, like dashboards, messaging and social media apps, trading screens, project boards.

A hypermedia system

hypereffect strives to be the world's second most successful hypermedia system, after HTML.

  • The server describes the UI. The client receives the interface itself, not data to interpret: it never parses contacts or orders and never needs to know what they mean in order to render them.
  • The server drives application state. Instead of a client-side store and router deciding what is possible, the server decides what the user sees and which actions are available next.
  • Behavior is declared in the markup. Each element describes the interactions it offers and where they go, so the document stays self-describing. Buttons and inputs in hypereffect are hypermedia controls: like links and forms, they declare their actions directly in their attributes.
