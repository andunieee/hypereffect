Server-driven UI, rendered natively

hypereffect

A simple protocol for describing server-guided, reactive interfaces that can be rendered anywhere.

  1. A client, the renderer, starts the session by sending hello. It knows nothing about the application yet.

    renderer → server 
    hello {}

  2. The server answers with the state, as signals, and a few elements. The renderer draws them with its own native widgets, in its own style.

    There is a fixed set of eighteen components, and they carry semantic variants, not styles: h2 or primary, never a colour or a margin.

    server → renderer 
    signal {"count":0,"_help":false}
element {"id":"main","type":"column"}
element {"id":"label","type":"text","parent":"main","variant":"h2","text":{"cel":"'Count: ' + string(s.count)"}}
element {"id":"inc","type":"button","parent":"main","variant":"primary","label":"Add one","onPress":{"action":"increment"}}

  3. Elements declare up front the few interactions they support. When the user acts, a handler can do only two things:

    • change the state locally, and every attribute that depends on it is recomputed: pressing Help sets _help, and the hint appears;
    • fire an action, like increment above.
    server → renderer 
    element {"id":"help","type":"button","parent":"main","variant":"plain","label":"Help","onPress":{"patch":{"_help":true}}}
element {"id":"hint","type":"text","parent":"main","variant":"caption","text":"Press Add one to count.","visible":{"cel":"s._help"}}

  4. Actions are sent to the server, with the current signals. Local signals, whose names start with _, stay on the client.

    renderer → server 
    action {"name":"increment","signals":{"count":0}}

  5. The server decides what happens next. It can send new elements, replace or remove existing ones, or send signal updates that are merged into the client's state, which may change the interface again.

    Here the label now reads Count: 1 without being re-sent: its text is an expression in Common Expression Language, which is safe, side-effect free and recomputed when the signals it reads change.

    server → renderer 
    signal {"count":1}
element {"id":"inc","type":"button","parent":"main","variant":"primary","label":"Add another","onPress":{"action":"increment"}}
remove {"id":"help"}

Embeddable anywhere

The components and interactions are few on purpose, so any app can render them inside itself: a game, a terminal program, a chat with an agent. The messages are lines of JSON over any transport that carries ordered bytes.

No client logic

Because the server guides everything, an interface can do a lot without a complex client or custom code: no JavaScript, and nothing to update in the renderer when the app changes.

A hypermedia system

hypereffect follows the ideas of Hypermedia Systems, outside the browser.

  • The same four parts as the web. A format (lines of JSON instead of HTML), a protocol (any ordered byte stream instead of HTTP), a server, and a generic client (a renderer instead of a browser).
  • Self-describing messages. Everything needed to show and operate the interface arrives in the messages, so one renderer displays every application and never changes when an application does.
  • Hypermedia controls. Like links and forms, components with an onPress or onSubmit say what triggers them and which action they send.
  • Responses are not tied to requests. An action is a command; the server answers with any number of patches on the same stream, which is the only way the interface changes.
  • The server is the engine of state. It decides which controls exist in each state. A renderer knows buttons and inputs, never contacts or orders, so features are added on the server only, with no client scripting.
  • Narrower than the web. No URLs or history: a session is one surface, and actions are names sent over it. No custom components or styles, so that every renderer can show every application.

Use cases

Interfaces that are mostly text, inputs, buttons and lists, with the logic on a server or in another process.

Sandboxed modules

A WebAssembly module with no screen writes hypereffect lines, and its host renders them.

Interfaces generated by agents

An LLM agent builds forms and choices on the fly, as plain JSON with no code to run.

Simple services without a custom UI

A service speaks hypereffect at a URL and looks native in any hypereffect client.

Control panels for hardware

A device serves its own control panel over a socket or serial line, with no web stack.
