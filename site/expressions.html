Expressions

Attribute values can be computed from signals with CEL expressions. The renderer re-evaluates them whenever the signals they read change.

CEL

Expressions are written in the Common Expression Language (CEL), a small language designed for evaluating untrusted expressions quickly and safely. It looks like the expression part of C, Java or JavaScript:

s.count + 1
s.user.name + ' (' + string(s.user.unread) + ')'
s.saved ? 'success' : 'failure'
size(s.items) == 0

CEL has no side effects and is not Turing-complete: evaluating an expression cannot change signals or send messages, and its cost is bounded by the size of the expression and its input. It has independent implementations in Go, Java, C++, Rust, JavaScript, Python and others.

Syntax

An expression is a JSON object with a single cel member holding the expression as a string. It takes the place of a literal value:

element {"id":"static","type":"text","text":"Hello"}
element {"id":"computed","type":"text","text":{"cel":"'Hello, ' + s.user.name"}}

Any other value is literal, including objects with other members or with a non-string cel.

"text":     {"cel":"'Count: ' + string(s.count)"}
"visible":  {"cel":"s.count > 0"}
"disabled": {"cel":"s._busy || s.login.user == ''"}
"variant":  {"cel":"s.saved ? 'success' : 'failure'"}

The s variable

Expressions have a single variable, s, which holds the current signals. With the signals {"count":3,"user":{"name":"Ada"},"_open":true}, the expressions s.count, s.user.name and s._open evaluate to 3, "Ada" and true. Keys that are not CEL identifiers can be read with an index, as in s['first-name'].

Where expressions are allowed

Any attribute may be an expression except the structural ones, which must be literal: id, type, parent, before, bind and the handlers (onPress, onChange, onSubmit, onDismiss). The component reference marks each attribute that accepts an expression.

Inside a handler, the leaf values of a patch may be expressions. They are evaluated against the current signals before the patch is applied, which allows a toggle:

"onPress": {"patch":{"_expanded":{"cel":"!s._expanded"}}}

Types

Signals are JSON, and are seen by CEL as follows:

JSONCEL
nullnull_type
true, falsebool
number with no fraction or exponentint
any other numberdouble
stringstring
arraylist(dyn)
objectmap(string, dyn)

CEL does not mix int and double in arithmetic. If a signal can hold either, convert it first: double(x) * 2.0.

The result must match the attribute's type. String and enum attributes need a string, with no implicit conversion, so numbers must go through string() or format(). Bool attributes need a bool. Number attributes accept int, uint or double.

Failure

If an expression fails to parse, fails to evaluate, or produces a value of the wrong type, the attribute takes its default. The renderer reports this as a diagnostic, never to the user.

Reading a signal that does not exist is an evaluation failure. The default of visible and open is true, so a failed expression shows the element. Send signals before the elements that read them, or test for them with has():

"text": {"cel":"has(s.user.name) ? s.user.name : 'guest'"}

The exact rules are in the specification.
