Concepts

hypereffect combines a few existing ideas. This page explains each one and how the protocol uses it.

Hypermedia

Hypermedia Systems describes a hypermedia system as four parts: a hypermedia format, a network protocol that carries it, a server that produces it, and a client that interprets it. On the web these are HTML, HTTP, a web server, and a browser.

hypereffect fills the same four slots with different parts:

PartWebhypereffect
FormatHTMLElement and signal messages (JSON, one per line)
ProtocolHTTPAny ordered byte stream; the application chooses
ServerWeb serverAny process that writes messages and reads actions
ClientBrowserA renderer: a library or program that draws the components natively

The important property, as with a browser, is that the client is generic. A renderer that can show one hypereffect application can show all of them. It does not need to be updated when an application changes, because everything it needs to display and operate the interface arrives in the messages. The book calls this property self-describing messages.

Hypermedia controls

A hypermedia control is an element that describes an interaction with the server. In HTML the canonical controls are the anchor and the form. Each control answers three questions: what triggers it, what request it makes, and where the result goes.

In hypereffect, a control is any component with an event attribute such as onPress or onSubmit:

element {"id":"archive","type":"button","parent":"row-7","label":"Archive",
         "onPress":{"action":"archive","payload":{"contact":7}}}
  • Trigger — the user presses the button.
  • Request — an action message named archive, carrying the payload, the id of the button, and the current non-local signals.
  • Target — whatever the server decides to patch in response. There is no fixed target; the result is zero or more element, remove and signal messages on the same stream.

The last point is a deliberate difference from HTML. A link replaces the page and a form replaces the page; htmx and Datastar let the response target a part of the page. In hypereffect the response is not tied to the request at all. This is the separation Datastar recommends under the name CQRS: actions are commands, and the stream of patches from the server is the single read path.

The server as the engine of state

HATEOAS — Hypermedia As The Engine Of Application State — means the representation the server sends encodes which operations are available right now. If a contact is archived, the server sends an Unarchive button instead of an Archive button; the client contains no rule about when each is valid.

hypereffect applies this directly. A renderer has no concept of a contact, an order or a user. It only sees buttons, inputs and text. Which buttons exist, and which actions they send, is decided by the server for each state. Adding a feature to an application means changing the server only.

This is also why the protocol has no client-side scripting. The renderer can evaluate expressions to decide what to show, and it can apply small local patches to signals (for example to open a dialog), but it cannot run application logic.

Elements and signals

The two primitives come from Datastar, which describes its approach as patching elements and patching signals from the backend.

Elements

An element is a JSON object with an id, a type naming one of the built-in components, and the attributes that component accepts. Elements that live inside a container name it with parent. The renderer keeps all elements in a tree indexed by id.

Sending an element message with an id the renderer already has replaces that element's attributes. Its children are kept, and so is local widget state: keyboard focus, scroll position, the text cursor in an input. This is the equivalent of Datastar's morphing. As with morphing, the recommended approach is to resend whole elements freely rather than compute minimal differences on the server.

Signals

Signals are a single JSON object shared between the server and the renderer. The server changes it with signal messages, which are applied as JSON Merge Patch: objects merge recursively, other values replace, and null deletes a key.

signal {"user":{"name":"Ada","unread":3}}
signal {"user":{"unread":4}}          # name is kept
signal {"user":{"unread":null}}       # unread is deleted

Input components write to signals through bind. When an action is sent, the renderer includes the signals, so the server sees what the user typed. Keys beginning with an underscore are local: they are never sent. They are for state that only matters to the renderer, such as which tab is selected or whether a dialog is open.

When to use which

Use elements for structure: what is on the screen. Use signals for values that change while the structure stays the same: a counter, a status, a validation message, whether a section is visible. Datastar's advice applies here too: keep signals few, and keep most state on the server. A signal is not a database.

Expressions

Attributes can be static JSON values or expressions in the Common Expression Language. An expression is written as an object with a single cel key:

"text":    {"cel":"signals.user.name + ' (' + string(signals.user.unread) + ')'"}
"visible": {"cel":"signals.user.unread > 0"}
"variant": {"cel":"signals.saved ? 'success' : 'failure'"}

CEL was chosen because its properties match what a renderer needs from an expression language running code from a server:

  • It has no side effects. Evaluating an expression cannot change signals, send messages or touch the host.
  • It is not Turing-complete, and evaluation time is bounded by the size of the expression and its input.
  • It has independent implementations in Go, Java, C++, Rust, JavaScript, Python and others, so renderers on different platforms can agree on results.
  • It is small enough to learn from a page of examples.

When a signal changes, the renderer re-evaluates the expressions that read it and updates the affected widgets. The server never has to resend an element for a value that is computed from signals.

Variants instead of styles

Components have no colour, font, size, padding or border attributes. Each component has a small set of named variants instead: a text can be h1, h2, h3, body, caption or code; a notice can be info, success, warning or failure.

This keeps the protocol portable. A terminal renderer might show a failure notice in red with a cross; a screen reader renderer announces it as an alert; a watch renderer might vibrate. Each is correct. It also means an application looks native wherever it is embedded, and that the host application's theme, contrast settings and accessibility settings apply without the server knowing about them.

Layout is similarly abstract. Containers have gaps of none, small, medium or large, and alignment keywords. The renderer maps these to whatever spacing its platform uses.

Indicators, not optimism

Because the server is the source of truth, a renderer should not pretend an action succeeded before the server says so. The protocol supports this through indicators: an event handler can name a local signal that the renderer sets to true when it sends the action.

"onPress":{"action":"save","indicator":"_saving"}

The server clears it when it has finished, typically in the same batch as the result:

signal {"_saving":false,"status":"Saved"}

Elements can use the indicator to disable a button or show a progress component. Local signals are not sent to the server, but the server may still write them.

Differences from the web

hypereffect is a hypermedia in the sense of Hypermedia Systems, but it is narrower than the web in several ways, and it is useful to be explicit about them.

  • No URLs or resources. Actions are names sent over an existing session, not requests to addressable resources. This makes hypereffect closer to a session protocol than to REST. Applications that want addressable screens can put a path in a signal or an action payload.
  • One connection, one screen. A session corresponds to one rendered surface. There is no history or back button in the protocol; if an application wants one, the server implements it.
  • No extension mechanism for components. HTML allows custom elements and scripts. hypereffect does not, by design, so that every renderer can display every application.
  • No styling. See above.
